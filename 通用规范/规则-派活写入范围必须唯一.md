# 派活写入范围必须唯一（2026-10-22）

## 一、规则

派给子 agent 的任务书里，**「允许写入的位置」只许出现一个白名单目录，只写一次**。

禁止出现这些句式：

- 「只许写 A，**或**追加到已命中的那份笔记」
- 「优先写 A，必要时可写 B」
- 「一般不要动 C，但如果……」
- 任何带「或」「必要时」「如果可以」的写入位置表述

**命中已有条目时怎么办**：一律先把“要追加的内容”写进 `_inbox\<任务名>\` 下的一个独立片段文件，由整理会话统一 merge 进正式条目。执行会话永远不直接改正式条目。

## 二、为什么（三次真实事故）

1. **2026-10-21 23:23 / 23:57**：一条线的任务书同时写了「只许写 `_inbox`」和「或追加到已命中的那份笔记」，而命中的笔记在 `D:\记忆\反馈\` 正式目录。执行方按前半句追加，直接写进正式目录两张反馈卡。**执行方无过错，根因在派单口径自相矛盾。**

2. **2026-10-22 凌晨**：另有一路把“备份”做成了改后内容（备份件与当前文件 md5 相同），回滚时等于没回滚。根因同样是动作顺序没写死（“备份”没说“必须在修改之前”）。

3. **2026-10-22 凌晨**：同一批 4 个文件被两个 agent 并发修改，因为派单方（主控）把同一个活派了两次，没有在飞任务清单。根因是派单前不查重。

三条事故的共同点：**不是执行方不听话，是任务书给了两个以上可能解释**。

## 三、自检（派活前逐条问）

1. 这条任务书的“允许写入位置”出现了几个？**必须恰好一个**。
2. 里面有没有“或”“必要时”“优先”这类词？有就删。
3. 这条活现在有没有别的 agent 在干？查过再派。
4. 涉及修改既有文件的，任务书里有没有写明“先备份、再修改”这个顺序？
5. 换一个平庸模型来执行，会不会做出与我预期不同的选择？会的话，说明还留了判断空间，拆细再来。

## 四、适用范围

所有派给子 agent 的任务，包括代码修改、文档修改、数据补齐、备份、迁移。**不适用于**只读排查类任务（那类不写任何位置，反而要写明“禁止写入”）。

## 五、工具坑：`_inbox` 默认搜不到（2026-10-22 实测）

`rg` / `ripgrep` 默认遵守 `.gitignore`，而 `D:\记忆\_inbox\`、`D:\Work\_inbox\` 都在忽略名单里。
后果：**"先搜后写"在 `_inbox` 上一直失效**——搜不到别的任务已放进来的产物，于是同主题多份笔记并行产生、互不知情。

已实证：2026-10-22 00:05 前后，同一主题在 `_inbox` 里出现 3 份不同措辞的笔记；当晚多份"先搜后写"的报告声称"未命中同主题条目"，其中一部分可能因此漏掉邻近件。

**正确做法**（任选其一）：
- 搜 `_inbox` 时加 `--no-ignore`
- 或显式把 `_inbox` 路径作为搜索根传进去
- 或改用不遵守 `.gitignore` 的检索工具

**「先搜后写」的完整口径应写成**：搜正式目录 + **显式搜 `_inbox`** + 搜历史快照（`.history`）。三者都搜过，才算"先搜后写"做到位。
