# 记忆投递单路纪律（禁止三头投递）

> 2026-10-23 由一次真实混乱定案：同一次"经验沉淀"被同一个 Agent 拆成三份
> ——① 项目 `docs\` ② `D:\记忆\_inbox\` ③ `ai-hub-memory` 的 `memory.py capture`，
> 三者格式不同、归属不同、内容重叠，审稿人要看三遍。
> 根因是投递方（当时的主控 persona）没有成文规则说明"该走哪条路"。

## 规则

### 1. 先分类型，再选唯一落点

| 知识类型 | 唯一落点 | 禁止 |
|---|---|---|
| **项目专属经验**（只对本项目有用的坑与结论） | 该项目自己的 `docs\` 目录，例：`D:\Work\经纬\docs\` | 不要再往任何记忆系统投 |
| **跨项目通用规则**（换个项目也成立的做法与纪律） | 只投 `D:\记忆\_inbox\<任务名>\`，等整理会话按判据审 | 项目 docs 里不要再写一份 |

### 2. 硬禁止

- **禁止同一批内容投递超过一个落点。** 投递前先自问：这条是"项目的"还是"通用的"？只能二选一。
- 拿不准归属 → **停下来问用户**，不要"两边都投一份保险"。
- 同一批内容因口径变化要重投 → 先在新 README 写明"以本目录为准"，**旧目录保留原样不删**，
  不要静默再出一份。

### 3. ai-hub-memory 是另一套系统

`D:\项目\ai-hub-memory` 的 `memory.py` 与 Obsidian 的 `D:\记忆` 是**两套独立记忆系统**，
互不同步、格式不同、归属判定机制不同。

- **未经用户在对话里明确要求，不许碰它**（`capture` / `settle` / `resolve` / `checkpoint` 全不许）。
- 尤其 `checkpoint` 会**自动 commit+push 入库**，等于绕过审稿直接落库。
- 它的路由是 fail-closed：`MEMORY.json` 里没有对应项目条目时，会投成 `project_hint: UNKNOWN`，
  需要 settler 人工判归属。**新项目要沉淀经验前，先在 `MEMORY.json` 注册户口。**

## 落点对照

| 系统 | 路径 | 定位 |
|---|---|---|
| Obsidian 个人记忆仓 | `D:\记忆` | front-matter + `索引.md` 体系；默认全只读，只投 `_inbox` |
| 工程记忆系统 | `D:\项目\ai-hub-memory` | `memory.py` 的 staging → settler → 晋升流程 |
| 项目自有知识 | `D:\Work\<项目>\docs\` | 项目专属，**不归任何记忆系统** |
