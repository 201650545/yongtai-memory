# 记忆库无人值守 · 总设计

> 真源 `D:\记忆`；工作资料库 `D:\Work`；索引引擎 `D:\Work\元智能\10_AI自成长引擎\技能库\local-knowledge-engine\`。
> 已有资产（不重造）：`id_alloc.py`、`scan_id_refs.py`、`obsidian-commit.ps1`、`cleanup.ps1`、`knowledge_eval.py`、`check_switcher_sync.py`。
> 硬规矩：执行会话不许 `git add/commit/push`；提交只走 `obsidian-commit.ps1`；写入只许落 `_inbox`；正式目录由整理会话合并。
> 本文件是设计，不含实现代码；文中命令行只调用既有脚本。

## 一、要达成的终局

**终局（一句话）**：人只做两件事——看报告、推翻决定；写入、去重、发号、校验、提交、巡检、裁决全部由四个角色按契约自动跑完，人只在「挂起队列」非空时被叫醒。

**不做人会怎样**（三条现状各有一条确定走向）：

| 现状瓶颈 | 不做人的走向 | 何时开始疼 |
| :-- | :-- | :-- |
| 提交（且厌恶提交） | 产物停在 `_inbox`，正式库与工作区永久分叉，真源失真、检索越查越旧 | 现在 |
| 冲突裁决（「不知道提哪个」） | 同主题副本持续增殖，每次查询都要人重判，裁决量随笔记数线性增长且不收敛 | 现在 |
| 格式校正 | 改号改规则 → 旧引用静默指错（已实证 6 处断链）→ 编号体系自身失去权威 | 每次改号 |

## 二、四个角色

四种职责，不是四个人；同一 agent 可兼任，但同一时刻只持一把锁（见 5.6）。

### 2.1 写作者

- **职责**：产出内容并投递；只判断「本次是否产生可复用结论」，不判断内容去哪。
- **允许写范围**：`D:\记忆\_inbox\<任务名>-<yyyyMMdd-HHmm>\`（命名依 `_inbox\README.md` 约定；同名目录已存在则换时间戳，不复用他人目录）。
- **禁止**：写 `_inbox` 以外任何路径；执行 `git add/commit/push`；进别人任务的 inbox 子目录；投递后自行删改自己已投递的文件。
- **失败处理**：目录不可建或写入被拒 → 内容原样留在会话输出并声明「未投递」，不重试第二次，更不退而写正式目录。

### 2.2 整理者

- **职责**：读 `_inbox` → 去重合并 → 发号 → 校验 → 经 `obsidian-commit.ps1` 提交 → 归档或清空该任务目录。
- **允许写范围**：正式目录的**新增**文件（合并结果）；`_inbox` 内自己正在处理的任务目录；自己的批次状态文件（见 5.2）。
- **禁止**：改写既有正式文件的正文（引用修正只出建议单，见 3.4）；自行 `git add/commit/push`；把 `_inbox` 内容整段搬进正式目录；跳过校验直接提交。
- **失败处理**：合并判定不了 → 进挂起队列，不提交该条；校验失败 → 整批退回 `_inbox` 并在批次报告记原因，绝不半提交。

### 2.3 巡检者

- **职责**：定时体检，发现漂移只报警，**不自动改任何文件**。
- **允许写范围**：`D:\Work\_inbox\巡检报告\<yyyyMMdd>\`（工作资料库，不污染记忆真源）+ 同目录 `ALERT.md`（仅 FAIL 时生成）。
- **禁止**：改正式目录；改 `_inbox` 内容；提交；把 WARN 直接升级成 ALERT。
- **失败处理**：体检项自身跑不起来（如脚本报错）→ 该项记为 FAIL 并写明「检查器不可用」，不静默跳过。

### 2.4 检索者

- **职责**：查询时按本地知识证据引擎的规范取证据（增量索引 + 混合检索 + 毫秒级抽取），给结论带出处。
- **允许写范围**：可选地把取数报告写到 `_inbox\<任务名>-<yyyyMMdd-HHmm>\`。
- **禁止**：把整篇正文灌进上下文；漫游全库逐文件读；引用库里不存在的编号 ID；无命中时用「印象」补答案。
- **失败处理**：检索零命中 → 明确报「无证据」，不降级为全文搜索；索引陈旧 → 先更新索引再检索，仍无命中才报无证据。

## 三、四条自动化主线

### 3.1 写入自动化

| 项 | 内容 |
| :-- | :-- |
| 触发时机 | 写作者判定本次会话产生了可复用结论（结论 + 出处 + 可被后续引用）时投递；纯过程日志不投递 |
| 落到哪 | `D:\记忆\_inbox\<任务名>-<yyyyMMdd-HHmm>\`，目录名唯一，一任务一目录 |
| 最小字段 | 文件头：`name`、`description`、`kind`、`status`、`scope`、`requires`；正文首段必须含：来源、生成时间、任务名、结论、出处（路径+行号 / 提交号） |
| 编号字段 | 若结论被别处引用，须带 `id_alloc.py` 发出的编号 ID（形如 `R-016`），不得自造 |
| 失败处理 | 写不进 → 内容留在会话输出并标「未投递」；不许降级写正式目录；不许重试到别的目录 |

投递判据由写作者自检：没有出处、没有结论、没有唯一目录，三者缺一即不投递。

### 3.2 整理自动化

- **何时跑**：每日固定窗口一次（建议 23:30，避开他人使用时段）；另加两个触发条件——`_inbox` 内任务目录数 ≥ 5，或有人工显式调用。
- **读什么**：`D:\记忆\_inbox\*` 全部任务目录；对每个候选主题，用本地知识证据引擎在 `D:\记忆`、`D:\Work` 两库取证据定位已有条目，**不漫游全文**；同时读既有正式条目。
- **判定规则**（逐条候选，顺序判定，命中即止）：
  1. 与已有条目结论一致 → 合并：把新增事实并入已有条目的**新版本文件**（新增文件，不改正文，见 2.2）；
  2. 同一主题但结论不同 → 交裁决自动化（3.4）；
  3. 主题不同 → 按 `scope` / `kind` 落到对应正式目录，作为新条目；
  4. 三条都不满足 → 进挂起队列。
- **冲突怎么办**：能自动定的按 3.4 定；不能定的**挂起**，该条不提交、不删除 inbox 副本，人来裁决。
- **提交怎么做**：合并结果落到正式目录后，**只把正式目录里的目标文件**交给 `obsidian-commit.ps1`，逐条显式路径，绝不 `git add -A`（`_inbox` 已在 `.gitignore`，不入库）。

  单文件：
  ```powershell
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File D:\小浣熊\mm-code\bin\obsidian-commit.ps1 -Repo D:\记忆 -Paths "参考\reference_信息源溯源_一手优先.md" -Message "docs: 合并 批次20261022-1"
  ```
  多文件（在 PowerShell 中调用）：
  ```powershell
  & 'D:\小浣熊\mm-code\bin\obsidian-commit.ps1' -Repo 'D:\记忆' -Paths @('参考\reference_a.md','流程\workflow_b.md') -Message 'docs: 合并 批次20261022-1'
  ```
  提交前预演（只读探测，不加锁、不写 git）：
  ```powershell
  & 'D:\小浣熊\mm-code\bin\obsidian-commit.ps1' -Repo 'D:\记忆' -Paths @('参考\reference_a.md') -Message 'dry-run' -DryRun
  ```
  锁被占时脚本退出码为 2，重试策略见 5.2。
- **归档**：提交成功后，把 `_inbox` 内该任务目录原文件移入 `D:\Work\_inbox\已归档\<批次号>\`，保留 7 天作回滚期（5.5），期满用 `cleanup.ps1` 按白名单清理临时产物（该脚本默认 dry-run，真删要 `-Yes`，且它不碰 `D:\记忆`、`D:\Work`）。

### 3.3 巡检自动化

- **检查项清单**（每项输出 PASS / WARN / FAIL）：

| # | 检查项 | 用什么 | FAIL 判据 |
| :-- | :-- | :-- | :-- |
| 1 | 编号唯一性与台账完整性 | `id_alloc.py check` | 出现重复号、缺号异常 |
| 2 | 编号引用可达性与唯一性 | `scan_id_refs.py --root "D:\记忆"` | missing > 0 或 ambiguous > 0 |
| 3 | 「第 N 条」式引用 | 全文扫描 | 命中 > 0 |
| 4 | 正式目录外写入 | 比对目录清单 | 执行会话产生的正式目录改动 > 0 |
| 5 | inbox 积压 | 目录计数 | 任务目录数 > 5 且上次整理未成功 |
| 6 | 提交锁与提交日志 | `commit.log`、锁文件 | 锁残留 > 10 分钟；同一文件被 add 两次 |
| 7 | 检索回归 | `knowledge_eval.py --mode regression --compare <基线>` | 命中集合低于基线 |
| 8 | 巡检自身心跳 | 心跳文件时间戳 | 距上次心跳 > 1.5 个周期 |

- **正常/异常判据**：全部 PASS = 正常；任一 WARN = 报告内记一行，不报警；任一 FAIL = 生成 `ALERT.md`。
- **报警渠道**：只写文件，不推消息——`D:\Work\_inbox\巡检报告\<yyyyMMdd>\ALERT.md`。人每天只看一个入口：**今天有没有 ALERT.md**。无异常的日子只留 `巡检报告.md`，不额外留告警文件，避免噪音。
- **误报怎么处理**：见 5.4。

### 3.4 裁决自动化

**证据分级优先级**（自上而下，先命中先定）：

1. **一手 > 二手**：一手 = 原始记录、实测输出、原始需求；二手 = 转述、复述、他人总结。
2. **有出处 > 无出处**：出处 = 可核路径 + 行号 / 提交号 / 原始文件名。
3. **新 > 旧**：时间真源是 **git 提交时间**（只读 `git log`，不做任何写操作）；未提交的新内容以整理批次时间为准。
4. 同级同分 → **不自动定**，挂起。

**能自动定**（写进批次报告，人可事后推翻）：

- A 一手且带出处，B 二手或无出处 → A 生效，B 标「被取代」。
- 两者结论其实一致，仅措辞差异 → 合并，不算冲突。
- 两者都已被上游规则废止 → 同时退役（`id_alloc.py retire`，号不复用）。

**必须挂起等人**：

- 两份都一手、都带出处、结论相反。
- 两份都无出处且互相矛盾。
- 涉及「规则该由谁拥有」的归属问题（跨库同一主题两份正式条目）。
- 涉及删除或改写既有正式文件正文。

**挂起标准格式**（文件落 `D:\记忆\_inbox\待裁决\<yyyyMMdd>\<序号>-<主题>.md`，字段缺一即视为格式不合格）：

| 字段 | 内容 |
| :-- | :-- |
| `id` | 挂起编号（自编 `H-001` 递增，不占用 `R/I/D/P/T` 号段） |
| `topic` | 一句话主题 |
| `candidates` | 候选 A / B：文件路径 + 行号 + 一手/二手标记 + 出处 + git 提交时间 |
| `conflict` | 冲突点：具体哪两句互相矛盾 |
| `evidence` | 已核证据：查过哪些文件、跑了哪个扫描器、结果如何 |
| `recommend` | 建议采纳哪一份 + 一句理由（**建议不等于决定**） |
| `ask` | 需要人回答的**单一**问题（多问即不合格） |
| `deadline` | 建议拍板日期 |

## 四、编号与引用规范

1. **单点发号**：编号一律由 `id_alloc.py` 分配，格式 `<前缀>-<三位序号>`（`R-016` 规则 / `I-` 想法 / `D-` 决策 / `P-` 踩坑 / `T-` 术语）。台账 `id_ledger.json` 是唯一号源。
   ```powershell
   python D:\Work\_inbox\编号分配器\id_alloc.py alloc --type R --note "无人值守：写作者投递字段"
   python D:\Work\_inbox\编号分配器\id_alloc.py retire R-016 --reason "规则废止"
   python D:\Work\_inbox\编号分配器\id_alloc.py check
   ```
2. **退役不复用**：`retire` 后的号占坑不再发；`ambiguous`（曾重号）单独标记，不作为有效引用目标。
3. **正文引用禁止「第 N 条」**：正文引用必须写规则标题或编号 ID（如「见《引用即校验》（R-016）」）。
   - **理由**：改号会让旧引用**静默指错**——引用仍「存在」、扫描器仍报有效，内容却指向另一条规则；已实证 6 处断链（见 `编号引用体检_20261022.md`）。写「第 N 条」等于把身份绑在位置上，位置一动即失效。
4. **引用校验纳入巡检**：`scan_id_refs.py` 的 missing / ambiguous 计数必须为 0；扫描结果进每日报告，FAIL 即报警。
   ```powershell
   python D:\Work\_inbox\引用扫描器\scan_id_refs.py --root "D:\记忆" --out "D:\Work\_inbox\巡检报告\<yyyyMMdd>\编号引用.md"
   ```
5. **存量整改**：现存 6 处断链做**一次性基线整改**（人工确认改法，整理者代提交）；此后新增必须为 0。

## 五、失败与降级（不许乐观）

### 5.1 定时任务没跑

- **怎么发现**：三重。① 巡检每轮读 Windows 任务计划程序里各任务的「上次运行时间 / 上次结果码」，超过 1.5 个周期即 FAIL；② 巡检自身的心跳文件超过 1.5 个周期即 FAIL；③ 人每天只需看一个入口——`D:\Work\_inbox\巡检报告\` 里最新日期是否 ≥ 今天减 1 天。
- **怎么办**：缺跑那一轮的产物不补算，直接判定该窗口「未执行」，下一轮照常跑；若连续 3 轮未执行，报警文案写「自动化已停 ≥3 周期」，不要写成「数据异常」。

### 5.2 提交脚本被占用或失败

- **占用**：`obsidian-commit.ps1` 抢不到独占锁（`D:\小浣熊\mm-code\.commit.lock`）时退出码为 2。整理者退避重试 **3 次**，间隔 60s / 180s / 300s；脚本自身对超过 10 分钟的陈旧锁会强制接管，人工不需手删锁。
- **失败**：push 失败由脚本内部 `pull --rebase` 后重试（`-MaxRetries`，默认 3）；仍失败则本批置为「未提交」，**保留 inbox 副本**，不删不改，下一批不包含它。
- **怎么不重复提交**：每批提交前把「目标路径列表 + 内容哈希」写入批次状态文件；提交成功后写「已提交 + 提交时间 + 目标清单」。重试前先比对状态文件：已在成功批次里出现过的路径直接跳过，避免二次 `git add`。脚本本身在「无暂存改动」时退出 0 且不重复提交，双保险。

### 5.3 发号器台账损坏

- **发现**：`id_alloc.py check` 报错或退出非零。
- **立即动作**：停发号（进入人工发号模式），已发号记录不作废。
- **恢复**（不依赖备份，因为号唯一性可从库内实况反推）：
  1. 全库统计已实际出现的 `R/I/D/P/T-xxx`，取各类型最大序号；
  2. 按台账既有 JSON 结构重建 `id_ledger.json`：已出现的号记为 `active`，曾重号的记为 `ambiguous`，明确废止的记为 `retired`；
  3. 跑 `id_alloc.py check` 验证无重复号、无异常；
  4. 从「各类型最大序号 + 1」恢复发号。
- **缺口**：`id_alloc.py` 现无 `rebuild/import` 子命令。**【待建】** 补一个 `rebuild --from-scan` 子命令，把上述 4 步自动化，避免人工手改 JSON。
- **恢复期间**：新条目的编号先记「待发号」，不占号、不留空。

### 5.4 巡检误报（狼来了）

- **只 FAIL 才出声**：WARN 只写在报告里，不生成 `ALERT.md`；人每天只看「有没有 ALERT.md」，噪音不进视野。
- **去抖**：同一告警指纹（检查项 + 对象路径）连续 2 轮出现才升为 ALERT，首轮记 WARN。
- **观察期**：新检查项上线后 3 天为观察期，期间一律降为 WARN，不报警。
- **已知例外**：人复核后把该告警标为「已知例外」写回巡检状态文件，巡检自动降级不再报；例外必须有原因和复查日期，不允许无理由静默。
- **反向约束**：连续 3 天无误报是验收判据（第六节第 4 条）；若误报频出，先下线该检查项，不靠调阈值掩盖。

### 5.5 整理者误合并

- **回滚窗口**：合并结果提交后，原 inbox 副本在 `D:\Work\_inbox\已归档\<批次号>\` 保留 **7 天**，期间随时可回滚。
- **回滚步骤**（不动 git 历史，只做一次正常提交）：
  1. 批次状态文件里查到该批的提交时间与目标清单；
  2. 只读取出合并前的版本内容（`git show <提交>:<路径>`，只读）；
  3. 把还原内容写回正式目录；
  4. 经 `obsidian-commit.ps1` 提交一条还原批次（回滚本身也必须走单写者脚本）。
- **回滚后**：该条自动进挂起队列，重新走 3.4 判定；相关 ID 标 `ambiguous`，等复核。
- **不做的事**：不删历史、不改写已有提交、不用 `git reset --hard`。

### 5.6 两个整理者同时跑

- **三道锁，顺序执行**：批次锁 → 台账锁 → 提交锁。
  1. **批次锁**【待建】：`D:\Work\_inbox\.organize.lock`，内容含 PID、批次号、时间戳；同一时刻只允许一个整理者进入「判定+发号+提交」段；超过 30 分钟视为陈旧可接管。
  2. **台账锁**：`id_alloc.py` 自带 `LedgerLock`，发号互斥。
  3. **提交锁**：`obsidian-commit.ps1` 的独占锁，保证入库单写者。
- **锁拿不到**：整理者**直接放弃本轮**（退出码 2 语义），下一窗口再来；不得排队等待后并发继续。
- **兜底**：批次锁未建好之前，阶段三/四只允许「单实例手动触发」，不接定时（见第七节）。

## 六、验收判据（可执行、可判定）

| # | 判据 | 判定方法 | 阈值 |
| :-- | :-- | :-- | :-- |

## 七、分阶段实施（按依赖排序，每阶段可独立验收）

- **阶段一 · 只读巡检（不改任何现有流程）**：巡检者上线，跑 `scan_id_refs.py`、`id_alloc.py check`、`knowledge_eval.py`，只出报告、不报警、不自动改、不碰提交。
  - 验收：连续 3 天产出报告；判据 3、6、10 全部有基线数据；现有流程零改动。
- **阶段二 · 编号与引用纪律**：写作者侧强制「不写第 N 条」并补投递最小字段；发号统一走 `id_alloc.py`；给 `id_alloc.py` 补 `rebuild --from-scan`【待建】；存量 6 处断链做一次性基线整改（人工确认，整理者代提交）。
  - 验收：判据 3、5、6、12。
- **阶段三 · 整理者半自动**：整理者只做「去重合并 + 发号 + 校验 + 生成提交清单」，**不自动提交**，人按清单用 `obsidian-commit.ps1` 提交；单实例手动触发。
  - 验收：判据 1、7、9。
- **阶段四 · 裁决自动化**：证据分级判定 + 挂起队列 + 挂起标准格式；冲突演练。
  - 验收：判据 8。
- **阶段五 · 全自动提交**：整理者自己调 `obsidian-commit.ps1`；批次锁【待建】上线后接定时；归档与 7 天回滚期生效。
  - 验收：判据 1、2、7、9 连续 7 天通过。
- **阶段六 · 报警闭环**：ALERT 通道 + 去抖 + 观察期 + 已知例外 + 心跳看门，误报压到 0。
  - 验收：判据 4。

依赖关系：一 → 二 → 三 → 四 → 五 → 六；每阶段未过验收不进入下一阶段。五（自动提交）放在最后，因为它是唯一会改变真源的不可逆动作。

## 八、明确不做的事

1. **不自动改写既有正式文件的正文**：改一个字都可能改变语义，改为出「引用修正建议单」交人裁决。
2. **不自动删除笔记**：`cleanup.ps1` 只清临时产物与日志，且默认 dry-run；`D:\记忆`、`D:\Work` 不在其清理范围，笔记删除永远是人或整理会话在提交前的显式动作。
3. **不引入向量数据库**：本地证据引擎已有词级 + trigram + 本地语义混合检索，再加一套只会制造第二个事实来源。
4. **不把发号挂在 git 提交上**：提交当前是流程末端且曾被厌恶，发号一旦依赖提交就会反向阻塞整理。
5. **不让 LLM 直接决定合并结果**：合并判据必须可复核（出处 + 时间 + 证据等级），模型只出建议，建议与决定分开存。
6. **不做多写者并发发号**：单机原子分配已够用；跨机场景靠批次锁串行化，不引入中心发号服务。
7. **不用「第 N 条」+ 稳定序列表**：那是被 6 处断链实证否掉的方案；正文引身份（标题或 ID），顺序交给文档内物理顺序。
8. **不建「每条规则一个目录」的深层目录树**：巡检、扫描、提交都要按路径枚举，深树会让断链和重复检查的成本线性上升。
9. **不把巡检结果推成打断式消息**：无人值守的报警只落文件，人自己按天看；推送会制造狼来了。
10. **不引入第三套事实来源**（另建台账、另建编号表、另建索引目录）：号源只有 `id_ledger.json`，提交入口只有 `obsidian-commit.ps1`。
