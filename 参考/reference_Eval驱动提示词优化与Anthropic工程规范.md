## 一、为什么靠“手感调参”必然失败

在生产环境中维护提示词时，最常见的误区是：
1. **感觉变好，实则回退（Regression）**：针对某一个 Bad Case 加了提示词补丁，感觉这个 Case 解决了，却暗中破坏了其他 9 个原本正常的 Case；
2. **自我催眠式加粗**：在 Prompt 中加上 `**务必保证 100% 准确**`、`**必须算对**`，模型不具备代码级心算能力，加粗无法凭空赋予算力；
3. **防御性补丁过度堆叠**：老版本模型能力较弱时写了大量负向规训（如“哪怕没有也不要乱猜”、“严禁主动调用”），新模型上线后依然保留这些补丁，导致模型过度避险、极度保守，正常信息也不敢输出；
4. **语义块混作一团**：规则、任务、背景资料、用户输入揉在同一段大文本中，导致模型注意力分散、语义边界模糊。

## 二、Anthropic 官方 5 大核心法则

### 1. 先做评估（Eval）再动提示词
* **法则**：在改动提示词之前，必须先用固定测试集考一遍，分清是新模型能力变了还是提示词有缺陷（两种情况的解法正好相反）。
* **量化验收**：改前改后跑同一套黄金测试集，用客观通过率（Pass Rate）和扣分项对比，不接受“感觉变好了”。

### 2. 用 XML 严格隔离语义块
* **法则**：如果你自己肉眼都分不清指令、业务规则与数据变量的边界，模型只会更混乱。
* **规范标签**：
  - `<instructions>`：系统核心指令与操作逻辑；
  - `<context>`：业务背景、长期记忆或静态规范；
  - `<constraints>`：必须遵守的硬约束与边界；
  - `<input>`：动态传入的用户输入或文件原文；
  - `<output_format>`：期望的返回结构定义（JSON Schema / 标签契约）。

### 3. 定期清理旧模型的“防御性补丁”
* **法则**：随着基座模型推理和遵循能力大幅提升，遗留的历史负向补丁会变成负资产。
* **动作**：升级模型或重构 Prompt 时，主动审视并剔除过度的防御性限制，释放模型的原生分析能力。

### 4. 指令无法凭空赋予模型能力
* **法则**：不要试图用自然语言“命令”模型完成它无法可靠完成的计算与核算。
* **解法**：算账、数据对比、精确统计果断剥离给 Tool Calling 或本地脚本执行，AI 只做调度与分析。

### 5. 业务权衡必须给全“博弈天平”的两端
* **法则**：只灌输单向操作成本会让模型极端避险（例如只写“转人工要花钱，尽量别转”，AI 就彻底不转人工）。
* **解法**：必须同时给出违约后果与潜在损失（如“虽有成本，但若客户退单损失更大，在此情况下允许转人工”），激活高智力模型的理性权衡能力。

## 三、本机落地纪律（规则 10 严格约束）

根据**负向硬约束（规则 10）**：“禁止用真模型做对比/压测/抽样验证——那是烧郭老师的额度，禁止批量调用真实模型”。

因此在本机工程中，Eval 驱动严格执行以下双层落地：
1. **第一层（离线静态规则体检 Prompt Lint）**：
   - 运行 `prompt_lint.py`，0 成本体检 XML 隔离、反模式与契约完备度，评分达到 75 分以上方可上线。
2. **第二层（离线契约断言 Rule-based Eval）**：
   - 建立黄金用例集，针对模型输出做必含项、禁含项与正则断言比对，毫秒级得出通过率。
3. **第三层（生产单次验证）**：
   - 确需验证真实模型效果时，单次使用最小请求（1 次），严禁循环发 20 轮。
