## 最终规则（照这四条执行）

1. **默认一个字都不写。** 没有用户在对话里明确说"你可以写 / 你可以改"，一律只读。
2. **正文永远只读。** 已存在的内容不许改写、覆盖、精简、删减、修错别字、顺手优化。
3. **获准后也不许写进正文。** 变更必须落到**与正文物理分开的变更副本 / 变更层**，
   让人一眼看出"哪里改成了哪里"。**不许在正文旁边打括号追加**（那仍属于写正文）。
4. **写之前先 grep 现有条目**，避免重复；同一事实不新建第二份。

## 为什么改成"独立副本"（他的理由）

> 「追加也不行，就是不能跟正文记在一起，要写在另外一边。」
> 「有一个正版正文记忆，然后有一个修改记忆……可以有一个记忆的副本，把修改内容记到那个记忆副本上去。」
> 「这样我用另一个 Agent 处理的时候，一眼就能看出来到底是哪里改到了哪里。」

⇒ 核心诉求是**可分辨性**：正文是权威、变更是候选，两者必须一眼可分。
⇒ 因此**整文件副本**也被否掉了——副本会立刻过期，且看不出"哪句被改了"。
⇒ 倾向的形态：**带锚点与基线的差异提案**（不是整文件复制）。

  在定稿前若要落盘，**先问用户用哪种形态**，不许 Agent 自行发明一套。

## 两个技术例外（可以动，但仅限这两处）

- `front-matter` 的 `status` / `superseded_by` 可更新，正文不许动。
- `索引.md` 是生成物，可被 `build_memory_index.py --build` 整文件重写，但**禁止手工编辑**。

## "提交"一词的歧义（必须分清）

此处的"提交"＝**追加记录**，**不是 `git commit`**。
执行会话禁止直接 git 提交的规矩仍然有效；需要入库走 `obsidian-commit.ps1`（单写者脚本）。
