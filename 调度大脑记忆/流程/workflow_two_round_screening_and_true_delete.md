# 两审制与真删：一套可以搬去任何"清库"现场的做法

筛选判据见 [[调度大脑记忆/反馈/feedback_content_retention_taste]]；本条只记**流程形状**——为什么值得单记：这套结构和他自己定别的删除流程（记忆库归档、skill 回收、死副本处置）用的是同一组原则，遇到新的"清一批存量"任务可以直接套。

**分工是硬边界**：助手逐篇讲透＋给**明确的**留/删预判，**最终判决归他**。助手不催、不说"按我说的删"、不期待建议被直接采纳；**一审阶段绝不修改任何数据**，只有拿到判决才执行。这条与"决策交给镜像 GPT"不冲突：内容取舍是他**亲自反复改判校准**过的领域，不外包给问诊。

**两种模式**：
- **模式 A 逐局深聊（默认 5 篇/局）**：从未保留且未标 `已呈现` 的条目随机抽 5 → 台账标 `已呈现`＋呈现日期 → 逐篇讲透 → 判决后立即四处同步 → 问是否开下一局。
- **模式 B 批量一审＋集中二审**：子代理分组读全文、助手复核改判后汇总，产出 `一审预判vN_日期.md`（速览表带**空白"二审判"列**＋详述＋**争议项置顶**）。批次大时另出结构化 `review_batch_<批次>.tsv`，用脚本生成单文件"二审判决台"滑卡页面；审完导出 `verdict_<批次>_final.json`。
- **判决台只产生判决文件，不执行删除**（键鼠为主，语音／手势是可选通道且数字映射与键盘相反）。拿到 verdict 仍走 dry-run→确认→apply。**入口与收取是自动的**：他只管"审完点导出"，由 watcher 脚本定期扫下载目录、校验后搬进 `_系统数据/verdicts/` 并接回流程，**不需要他回报路径**。

**真删＝四处同步、不留副本**（本项目口径）：① 全文文件 ② 台账 JSON 条目 ③ 映射 JSON 条目 ④ 云端表格行。结构化批次还要加第 ⑤ 处（分类目录里的 md）。**判留**则是台账写 `保留/保留时间/保留原因`（记他的原话判据），并收录进精选库、同步篇数计数。

**执行范式（这三步是防错的关键，别省）**：
1. 临时脚本内写死 DROP／KEEP 集，先 **dry-run** 校验"台账·映射·全文三件齐全"；
2. 齐全才 `--apply`；
3. 再用**独立校验脚本**扫四类孤儿（台账有·全文缺／映射有·全文缺／反之／映射值不是预期前缀）。

**ID 绝不从人或子代理的输出手抄**——本项目真出过事故：24 位 ID 被少抄 1 位。判据：**先写临时文件再读，删除集一律用"JSON 实际键集合减去 KEEP 集"算出来**。这条与我自己的"用不可猜令牌证明实读"是同一个防线的两端。

**批次结业要留反悔护栏**：`_knowledge_base.json` rows 清空、只留结业标记；目录／看板／图谱降级为历史快照；**并写明"勿复用已结业批次、勿再跑构建脚本"**——否则下一次构建会把已删的全文卷回来。
