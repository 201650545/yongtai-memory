# 字段产权：一份数据只允许一个人格可写

这条不是"小红书怎么同步飞书"，而是他整个体系防**双份真相**的做法，与 handbook 的 SSOT 法、与元智能「每个层只有一个可写真源」是同一条定律的三个化身。**新场景要接第二个存储（飞书／Notion／数据库／另一个仓）时，先画这张表再写同步代码。**

**四步（2026-09-23 镜像 GPT Extended 问诊给出，他采纳后落地）**：
1. 给每条记录一个**永久 ID**（这里是笔记 ID，文件名即 ID）——没有永久 ID 的同步等于用标题对齐，迟早错配。
2. 把字段分成三类：**内容事实**（全文／分析／标签／链接／路径）、**行动状态**（意图／优先级／下一步／到期日／产出物链接）、**派生**（序号／分类／公式）。
3. 每类指定**唯一可写端**，方向写死：本地写内容事实 → 单向投影到只读镜像；行动状态只在镜像改，本地只留 AI 初始快照、**不当当前真相**。
4. 两条元规则：**同一个字段只有一个地方允许人工修改**；**AI 只预填、不写终值**（终值永远由人拍板）。

**"要不要留第二套"的判据是实测，不是设计**。本项目原先设计成"飞书主"8 个行动字段，观察期（2026-09-24 收口）结论是**他从未在飞书拍板、行动字段零交互**——于是飞书整体降级为单向上行的只读云镜像，原 8 个"飞书主"字段保留在表里但**不再有流程意义**。
→ 通用启示：**先跑 2~4 周看他在哪一侧真的完成"拍板→行动→产出"，再决定砍谁**。任何"两边都能改"的设计，实测一定会退化成两边都不改或改坏一边。

**顺序即正确性**：新内容**先落本地主库 → 再生成镜像投影**（本项目已是此顺序）。反过来做（先从镜像建记录、再补全文）会让镜像成为事实上的主库，产权表立刻失真。
