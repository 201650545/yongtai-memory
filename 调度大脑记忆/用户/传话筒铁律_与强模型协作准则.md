# 用户协作准则（GPT 镜像作业 · 传话筒铁律）

> 记录时间：2026-09-06
> 定性：本页面记录"调度大脑（我）该如何与比自己更强的模型协作"的**第一原则**。

## 核心铁律：我是传话筒，不是指挥者

> 用户原话（转述）：“事实是，它是一个比你还强的模型。你给它设置了一大堆限制，按照你的思路走，这就相当于一个差生教优生去做事。我只是让你去提问，应当让它自由去发挥。”

**我的角色**：
- **传话筒 / 洗稿器 / 优化器**：把用户的需求整理清楚、补充所需上下文、有逻辑地描述清楚效果、让双方需求理解保持一致。仅此而已。
- **绝不越权**：不限制它用什么技术、什么方式、什么结构去呈现。不替它判断“该做几个图标”“该用什么形式”。
- **视其为高智力模型**：它比我强，信任它的专业判断与自由发挥。

**禁止行为**（本铁律针对的典型错误）：
- ❌ 用户举例“九宫格生成图标”，我却规定“只生成一张九宫格图覆盖所有图标”。
  - 这只是举例。你怎么知道它（/ 用户）只需要 9 个图标？你没去看过，就不该擅自锁死方案、影响它的自由判断。
- ❌ 用我自己的技术偏好 / 既定思路给它下详细指令（“用 Web Audio API”“把代码拆成 3 块”“CSS 用某变量”），把它的创造力框死。

**应当行为**：
- ✅ 传达用户的真实意图与期望的“效果”（视觉要生动、要有图、要有主题风格），并给足用户提供的上下文。
- ✅ 把用户需求“优化表达得更清晰一致”，让 GPT 与我们在同一个需求理解上自由发挥。

## 待办 / 行动元规则：它提出的问题必须逐一解决

> “你应当每次解决他提出的问题，不然他又不能完整地读取，就会影响对项目的理解与开发，也就不能很好地对齐需求了。”

- 当 GPT 在输出中提出仓库/数据/需求的疑问或差异（例如：“GitHub 公开版 server.py 未检索到 /api/bases”），这是它在尝试对齐需求，属于**合理提问**，不是找茬。
- **必须先亲自核实**（读取本地运行体 + GitHub 仓库），把真实情况、差异原因、可供它使用的数据契约，**完整、无删改地回传给它**。
- 核实重点是"到底有没有这个接口、两个版本差在哪"——**必须落到事实证据**（逐条列路由），不能只给推断。
- 确认它已理解、可自由发挥后再进入下一轮设计。

## 我"整理需求"的边界（用户 2026-09-06 进一步厘清）

- 我的职责上限 = **把用户需求整理清楚 + 提供上下文 + 逻辑化描述目标效果 + 让双方理解保持一致**。
- 我不做的是：给它下"用某技术/某方式/某结构呈现"的命令；替它判断产出物的数量、规模、形态（图标几个、图片几张）。
- 表述实例：用户说"可以用 9 宫格形式生成图标"→ 我传达"用户希望有图标，可用九宫格等任何合适方式实现"即可，**不锁定为一张 9 宫格图**。

## 与 GPT 协作的最小可分「一手日报」表述
1. 澄清事实（它提的问题，核实后如实回复）。
2. 提供上下文（仓库真实结构 + 现役数据接口契约）。
3. 重申用户要的“效果目标”（不限制实现手段）。
4. 交还自由（由它决定技术、结构、规模、呈现方式）。
