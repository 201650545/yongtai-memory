# 本地应用接 AI：走网关直连，不刷官网

## 结论（判据）

**本地运行的前端应用（HTML 小游戏、工具页）需要 AI 推理时：**

1. **优先用本机网关直连**，别用 opencli / CDP 自动化去刷 DeepSeek 官网或 ChatGPT 镜像站。
2. **网关 CORS 放行就前端直连，不做本地转发服务**。本地后台服务在 Agent 会话结束后会被系统回收，是"点了没反应 / 推演失败"的根源（本次踩过）。
3. 前端直连时密钥写在前端（本机自用、非公开交付，可接受）；网关不可用时多模型 + 多网关兜底。

## 本次实证（2026-11-18）

- 郭老师原方案：opencli 把问题和提示词发 DeepSeek 官网，"白嫖算力且不触发风控"。
- 查证否决：`chat.deepseek.com` 实测 **HTTP 429（限流）**；脚本化刷正是风控目标，"不触发风控"前提不成立，封的是自己的号。
- 本机 `3100 search_gateway`（key `gyt2005228`，配置在 `D:\项目\ai-hub\search_gateway`）现成有 `deepseek` 模型（返回 `deepseek-v4-flash-0731`），免费、秒回、CORS 全放行（`Allow-Origin: *`、`Allow-Headers: Content-Type, Authorization`、OPTIONS 200）。
- 改用 3100 直连后：真实浏览器从 `file://` 打开 HTML 走完整流程 10/10 通过，AI 返回战况/归因正常，零风控风险。
- 中途踩坑：先做了本地转发服务（server.py + 8931 端口），服务在会话结束后被回收 → "推演失败"；发现网关 CORS 全通后砍掉服务，前端直连根治。

## 边界（与已有结论不冲突）

- **不推翻** `反馈/feedback-向外求先问镜像站与DeepSeek官网.md`：那条管"向外求信息/图片风格/灵感该走哪个通道产出交付物"；本条管"本地应用内嵌 AI 算力该走哪个通道"。 DeepSeek 官网 skill 用于**人/Agent 主动搜资料**，不是给本地程序当后端 API。
- **不违反** `feedback_浏览器操作必须静默不抢用户画面.md`：本条压根不操作浏览器去刷官网。
- 与"`web_search` 按次计费硬禁"也不冲突：本机网关是自有/已有渠道，不花搜索额度。

## 适用范围与例外

- 适用：本机自用、不公开交付的 HTML 工具/游戏；网关需常驻运行。
- 例外：若做的是**要公开发布**的应用，密钥不能硬编码前端，应走后端代理 + 密钥管理；此时"本地转发服务"的必要性要重新评估（但仍不该刷官网）。
