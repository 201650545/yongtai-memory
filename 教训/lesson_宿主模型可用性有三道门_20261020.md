# 教训：模型"可用"有三道门，直连通 ≠ 宿主能用

## 一、症状

2026-10-20 晚，为了省配额把经纬的 worker 模型从 `workbuddy/deepseek-v4.1-flash`（x0.11，配额耗尽）
换成看起来更便宜更快的 `workbuddy/glm-5.3-flash`（x0.08，2.4s，输出干净）。

- **直连 buddy2api 完全正常**：`credit=0/0.08`，2.4s，输出正确
- **function calling 也正常**：给它一个 `write` 工具定义，能正确返回 `tool_calls`
- **但通过 DSH 子代理跑就必然失败**：节点永远 `status=failed`，`error` 只有一个字 `error`

连续换 5 个模型档位全部失败，总耗时 17.7s（约等于 5 次尝试），
一开始我以为是"宿主没热重载"，其实**每一档都真的跑了，只是全灭**。

## 二、根因：第三道门是 reasoning 声明

DSH 发起子 Agent 时默认带 `reasoningEffort = off`。
而 provider 配置（`~/.dsh/profiles/desktop/cordis.patch.yml`）里，
**只有显式声明了 `reasoningEfforts: { 'off': null, ... }` 的模型才接受 off**：

```yaml
- id: workbuddy/hy3                    # ✅ 声明了 off
  reasoningEfforts:
    'off': null
    low: low
    high: high

- id: workbuddy/glm-5.3-flash          # ❌ 没声明 off
  reasoningEfforts:
    low: low
    high: high
    max: max
```

拿没声明 off 的模型当 worker ⇒ 宿主直接返回 `stopReason='error'`，
而且**错误信息被吃掉，只剩 "error" 两个字**，极难定位。

## 三、模型可用性 = 连过三关（这是本次的核心判据）

| 门 | 验什么 | 怎么验 | 不通的表现 |
|---|---|---|---|
| ① 倍率/配额 | 花不花钱、还有没有额度 | `usage.credit` 字段 + `x0.08` 这类标注 | 429 / "earliest reset at ..." |
| ② 能力 | 会不会 function calling（worker 要写文件） | 带 `tools` 定义发一次，看有没有 `tool_calls` | 只回文本、不调工具 |
| ③ **宿主契约** | 宿主默认参数它认不认（如 reasoning=off） | 查 provider 配置里该模型的 `reasoningEfforts` 有没有声明宿主默认值 | `stopReason='error'`，无有效错误文案 |

**只验 ①② 会得出"这模型能用"的错误结论。**

## 四、修法（两件事）

1. **选对模型**：零倍率里同时满足三关的只有 `workbuddy/hy3`（x0、声明 off、支持工具、2s）。
2. **加降级链**：`workerFallbacks` 逐档重试，但**只在「没跑起来」时换档**；
   产物缺失不换档（那是 prompt/路径问题，换模型也没用，还会掩盖真因）。
   并且把**实际用上的模型写回图里**（`node.model`）+ 记 `fallbackTried` 轨迹 ——
   否则画布上「来源」那一行会撒谎，显示的还是首选模型。

## 五、可迁移的判断力

1. **"直连 API 通"只证明服务端通，不证明宿主能用**。宿主会加自己的默认参数、系统提示、
   工具集、鉴权映射 —— 每一样都可能成为拒绝的理由。
2. **错误信息被吞掉时，用"耗时"反推尝试次数**。17.7s ÷ 单次 ~3s ≈ 5 次，
   这个算术直接推翻了我"没重载"的误判。
3. **同一批候选要建矩阵一次性比完**（倍率 × 工具 × 宿主契约 × 延迟），
   而不是挑一个试一个 —— 试一个改一次代码，每轮都要等热重载，极慢。
4. **降本时"最便宜"不等于"最省事"**。x0 但没声明 off 的模型，省下的是钱，付出的是排查时间。
5. 顺带：**改插件源码后要看宿主是否真重载**。判断办法不是看文件 mtime，
   而是看**行为里有没有新字段**（比如 `fallbackTried` 出不出现）。这次就是靠它发现宿主还在跑旧代码。
