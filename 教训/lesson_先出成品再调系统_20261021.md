# 教训：先出成品，再调系统；跑真活用稳定渠道

## 一、原话

> 「好久了，你都没有把成品做给我，我都要上课了。记住这一条啊，下次优先把成品做给我，然后你调此智能体的时候你优先去调用一些 BUDDY 中稳定的渠道去干这些活呀」

## 二、我做错了什么

2026-10-21 上午，郭老师给了一份完整到可以直接施工的《呼吸的变化》2 页 A4 规格，让我"用这个测一下节点能不能做"。

我的实际路径：
1. 建风格卡 → 2. 做风格节点 → 3. 画布选风格 UI → 4. 反复重载插件 → 5. 追查模型链为什么失败 → 6. 跨 provider 定位故障……

结果：**一个多小时，她一张纸都没拿到**。而按她的规格，我完全可以用 10 分钟直接把 2 页 A4 做出来。

**根本错误：我把"测系统"当成了任务，其实她的任务是"要一份能上课用的材料"。**

## 三、两条硬规则

### 规则 1：先交成品，再做验证
- 有明确交付物时，**先用最短路径把成品做出来交给她**，再回头做系统层的验证与调优。
- "测节点能不能做"不等于"必须用节点做出来才算数"——先用别的方式交一版，再用节点做一版对比，才是对的顺序。
- 判断标准：**她手上有没有能用/能打印/能发出去的东西**。没有就是没交付。

### 规则 2：跑真活用稳定渠道
- 2026-10-21 实测（buddy2api）：
  - **稳**：`raccoon/sn-deepseek-v4-1-flash-1017`（115s，可用）、`local-gateway/high`（22s，可用）
  - **不稳**：`workbuddy/*` 全线（hy3 / hy4 / step-5 / glm-5.3-flash / deepseek-v4.1-flash / spark-x2.6）当 DSH worker 时大面积失败
- 所以：**做真活（要交付的）先用 `local-gateway/high` 或 `raccoon/*`；调优实验才去试便宜/免倍率的渠道。**
- 倍率便宜不等于总成本低：为了省几分钱把 40 分钟耗在重试上，是净亏损。

## 四、可迁移判断力

1. **有截止时间时，"能不能用"优先于"是不是我的系统产出的"。** 交付物 > 方法论。
2. **排查故障要设止损线**：连续两次以上同类失败，就先绕开（换渠道/换实现），别一条路挖到底。
3. **先问"她拿这个要干什么"**：她说"测试一下能不能做"，真实约束是"我马上要上课"。识别出真实约束，路径会完全不同。
4. **做一份"退路"再开工**：任何可能跑很久的实验，先花 10 分钟做一个人工保底版，心里就不慌。
