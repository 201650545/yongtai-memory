# 「没跑」与「没产出」应收敛成同一个信号：心跳缺席

> **一句话结论**：「没跑」与「没产出」应收敛成同一信号：心跳缺席。

## 一、现象（真实数字与口径现状）

1. **同一个「这活儿到底行不行」的问题，现在分属两个地方判**：
   - 「**没跑**」由 Windows 计划任务侧回答：上次运行时间、上次结果码；
   - 「**没产出**」由产出级断言回答：产物在不在、内容对不对。
   两套口径各管一半 ⇒ 读报告的人要同时看两处才敢下结论，而**两处都「正常」时的组合才是最危险的**。
2. **本轮被真实故障印证了「跑了 ≠ 产出」**（改造后 2026-10-22 08:00 前后：`asserted_green = 13`、`process_only = 11`、`asserted_fail = 2`、`unknown = 0`）：
   两条 `asserted_fail` 是真实失败——`balancewatch` 的 `quota_guard.json` 停在昨天；`modelscope_daily_guard` 的 `"all_granted": true` 只在 2026-08-10~13 出现过，已约 10 万分钟未更新。
   **这两条的共同特征就是：进程跑了、退出码没炸，但没有「本轮的产出」。**
3. 剩下 `process_only = 11` 条更危险：它们**连「产出级」都没查**，所以连上面那两条的命都发现不了——没被断言覆盖的失败，在这个口径下是**不可见**的。
4. **说明**：本主题（「心跳缺席」作为统一信号）是本轮**三方调研收敛**出来的机制，**尚未在本机落地**；上面第 1、3 条是它要解决的口径现状，第 2 条是它要覆盖的真实样本。本主题因此**不另造数字**，只引用本轮已实测的数字。

## 二、为什么是问题

- **「没跑」和「没产出」在业务上是同一件事的后两种说法**：我要的是「产出」，没跑只是它的一种成因。
  分开判的代价是：两套口径的**交集会漏**——「跑了但没产出」既不是「没跑」也不是「断言红」（因为没有断言覆盖它），它掉进两套口径之间的缝里。
- **心跳如果由任务自己写，就会自欺。** 任务自己写心跳 ⇒ 任务自己决定自己活着；一个「跑起来就写心跳、但产出是空壳」的任务，心跳永远是新的。**心跳必须是断言的结果，不是任务的自报。**
- **「应到未到」比「失败了」更早**：任务挂死、机器休眠、脚本卡住时，退出码还没变，但心跳已经缺席了。等到退出码非零才发现，损失已经是「一整个周期没产出」。
- **UNKNOWN 必须是一个独立状态**：没跑到就既不是成功也不是失败。把它算成成功是假绿，算成失败是假红。

## 三、对策：三方调研收敛出的做法

### 3.1 三个已核实项目给出的同一件事

| 来源 | 机制 | 收敛出的可复用点 |
| :-- | :-- | :-- |
| `healthchecks` | **应到未到**：到期没收到心跳就告警，而不是等对方自己报错 | 缺席是**一等公民信号**，不依附于失败信号 |
| `dagster` | **AssetCheck 把检查绑在资产上**；资产没被物化时状态是 **UNKNOWN**，不是成功 | 「没产出」必须有独立于成功/失败的第三态 |
| 共同实践 | **先断言、再写心跳**：心跳是断言通过之后才写的 | 心跳 = 判定的**结果**，不是任务的**自报** |

（另有 `uptime-kuma` 这类心跳式监控可参照「按周期判活」的思路；此处只取思路，不引具体实现。）

### 3.2 收敛后的三条落地规则

1. **心跳缺席 = 唯一的主信号**：一条受监任务在「本轮应到之后」没有收到心跳 ⇒ 报「应到未到」。
   「没跑」与「没产出」在这一层被**塌缩成同一个信号**；具体成因（没跑 / 跑了没产出 / 跑了产出是旧的）由独立验证器在下一层细分。
2. **先断言、再写心跳（顺序不可换）**：验证器先跑产出级断言 ⇒ 通过才更新心跳文件 ⇒ 心跳新鲜度就等价于「最近一轮断言通过」。
   断言失败 ⇒ **不写心跳**（让缺席自然发生），而不是写一个「我失败了」的心跳。
3. **防自欺：断言由独立验证器执行，不由任务自报**。职责切分：
   - 任务：只负责产出，不写心跳、不自报绿；
   - 验证器（探针/巡检侧）：读产物 → 跑断言 → 写心跳 → 报状态；
   - 消费方（人、巡检报告）：只信验证器写下的状态与心跳，**不采信任务的自述**。

### 3.3 与 UNKNOWN 三态的对齐

| 情况 | 心跳 | 状态 |
| :-- | :-- | :-- |
| 断言通过 | 更新 | 绿（`asserted_green`） |
| 断言不通过 | **不更新**（⇒ 缺席） | 红（`asserted_fail`） |
| 本轮不该跑 / 没有产出可断言 | 不更新 | `unknown`（单列，不计入绿、不算红） |
| 到期仍无心跳 | 缺席 | **应到未到**（缺席信号；成因待查） |

## 四、验证方式（含负例验证）

**正例**

1. 独立验证器跑一轮 → 心跳文件 mtime 更新，且心跳内容里的状态与断言结果**逐条一致**（断言通过的有心跳，失败/未到的没有）。
2. 故意让某条任务「本轮应到但没跑」→ 心跳保持旧时间戳 ⇒ 缺席被检出，报「应到未到」。
3. 缺席信号与断言红**不混淆**：断言失败的任务报的是「红 + 原因」，缺席报的是「应到未到」，两者在报告里分节呈现。

**负例验证（关键，没有负例就等于设计了一个自欺系统）**

1. **自欺负例（最重要）**：让任务**照常写心跳**，但把它的产出停掉（不产出 / 产出内容停在旧值）→ 验证器必须把该条判红／不更新心跳。
   **若报告仍然显示绿、心跳仍然新鲜 ⇒ 心跳被任务自报 ⇒ 这套机制自欺成立，必须重做。**
2. **顺序负例**：把「先写心跳、后跑断言」的实现换回去 → 心跳新鲜度不再等价于「断言通过」，缺席信号立刻失去意义（须由独立的顺序断言守住）。
3. **UNKNOWN 负例**：把一条 `unknown`（本轮不该跑 / 无产出可断言）的任务强行纳入「应到未到」判据 → 它必须被排除在缺席告警外，**既不当红也不当绿**。
4. **探针失效负例**：让验证器自己跑不起来（脚本报错 / 产物过期）→ 消费方必须报「本次不可采信」，**不得**把「没有缺席读数」当成「一切正常」。
5. **时钟/休眠负例**：机器休眠跨过一个周期 ⇒ 心跳必然缺席；系统必须能区分「机器没开机」与「任务没跑」，否则会造出一片假红（Windows 计划任务环境下这一条尤其容易踩）。

## 五、适用边界

**成立的环境**

- Windows 本机 + PowerShell 5.1 + 无 Docker / 无 k8s + 调度靠 Windows 计划任务。
  没有编排层提供 liveness/readiness，**心跳文件 + 计划任务上次运行时间**是唯一可用的「活着吗」信号。
- 任务有稳定的调度周期，能定义「应到」（本轮应到时刻 + 宽限期）。
- 产地在本地且可被独立验证器读取。

**不成立 / 需要换做法的情况**

- 已有编排层（k8s / ECS / CI）提供 liveness probe、healthz、重试与退避语义 ⇒ 直接用编排层的，不要自己造心跳。
- **周期跨度大于一天**或周期不规则的任务 ⇒ 「应到未到」窗口必须大于任务周期，否则全是噪声。
- **一次性 / 人工触发**的任务 ⇒ 不适用心跳缺席，应改用「到期该产出却没有」的产出级断言（见《绿分两级》那条）。
- 产出在远端且不可拉取 ⇒ 心跳只能证明「验证器跑到了」，不能证明「产出对」；此时必须先解决产出可读性。
- 进程型常驻服务 ⇒ 用进程/端口存活判定，心跳文件属于多余抽象。
