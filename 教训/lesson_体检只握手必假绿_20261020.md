# 教训：只握手＝假绿；自检的基准数与哨兵会自然失效

## 一、症状

`mcp\search_mcp_server.py` 的后端写死 `http://127.0.0.1:3000`，
而 `:3000` 搜索网关已于 2026-10-11 被裁定 **skill 化**（无进程、无端口、无自启）。
⇒ 走 MCP 真调 `search` / `aggregate` 必然返回"无法连接搜索网关"。

**可它一直是绿的**：`_probe.py` 只做 `initialize` + `tools/list`，**从不真调工具**；
每日体检 `capability_probe.py` 同样只握手 ⇒ 一条"真调必失败"的能力被连日判成 `alive`。

## 二、根因（两条，别只记一条）

1. **握手 ≠ 能用**：`initialize`/`tools/list` 只证明**进程能起、工具已注册**，
   证明不了**工具调得动**。凡是"客户端写死了一个地址"的服务，必须有一条**真调**的探针。
2. **自检的基准数与哨兵会随环境自然失效**（同一天踩到第二例）：
   - 死链枚举器的 `expected_total: 946` 是 2026-09-24 的环境快照；宿主环境被清理/改名后
     真值变成 **446**，两条独立实现**对不上** ⇒ 枚举器一直 `exit 3`，清单"不可采信"。
   - 哨兵链接 `.trae\skills\ad-creative` 被母仓化改名**修好了**（现在能走通）⇒
     "必须检出这条已知断链"永远检不出 ⇒ 普查器也一直 `exit 3`。
   - 冒烟配置的数量下限（重名≥50／哈希≥150／断链≥100）也随宿主清理而过期，
     于是**机器变干净了，探针反而报"探针坏了"**。
   ⇒ **凡是把"当前环境的数字"写进判据的地方，机器一变就腐烂。**

## 三、反过来的教训：别凭"上一轮的诊断"改代码

上一轮交接单写的是"普查器把非链接条目当链接判，946 条大部分是假阳性"。
**先量再改**（两条独立口径对跑）后发现：
普查口径（ReparsePoint+活性探针）＝446，枚举口径（读记录目标+目标不可达）＝446，**0 偏差**
⇒ **探测逻辑没坏，坏的是写死的基准与哨兵**。
差一步就会去"修"一段本来正确的检测逻辑。

**方法**：改探针前，先用**两条互相独立的通道**测同一个量，对得上就别动逻辑，只重校基准。

## 四、正确的做法（可复用）

1. **探针分三层**：①进程能起 ②工具已注册 ③**工具真调得出结果**。
   只有 ③ 才能判"能力可用"；体检口径必须写清楚自己探到哪一层。
2. **真调要挑零成本通道**：本次用 `hackernews`（HN 公开 API）——
   不占浏览器、不需登录、**不触付费 LLM**（`content_pool.run_search` 只做引擎采集＋内容池＋报告，不调 LLM 整理）。
   ⚠️ 别拿付费 key 的渠道做每日真调。
3. **基准与哨兵要么改成"合成自检"，要么标上实测日期与出处**：
   合成自检＝拿一个**保证不存在**的路径喂给活性探针，它必须判"断"；
   再拿一个**保证存在**的目录喂给它，它必须判"通"——这样不依赖磁盘上还有没有那条坏链。
4. **判据与地板分开**：`levels.*`（预警线/熔断线）＝郭老师定的判据，**一个字不动**；
   `self_test.*` 下限＝探针自检的下限（证明链路跑出了量），**该随环境校准就校准**，
   并且要写清楚"为什么从 X 调到 Y、实测值是多少"。
5. **可交叉验证的实现要留两条**：一条判"断不断"，一条判"断成什么样"（枚举器分 ORPHAN/UNREACHABLE），
   逐宿主计数硬比对（tolerance=0）——对不上就说明其中一条坏了，而不是"环境变了"。
