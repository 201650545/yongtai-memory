# 追加片段 · 声明自己会腐烂 —— 声明也要接受机器检查

> **一句话结论**：声明会腐烂：没人消费的 baseline、多分母、三豁免叠加都会静默失真。

> ⚠️ **本文件是追加片段，不是独立条目。**
> **建议追加到**：`D:\记忆\教训\lesson_体检只握手必假绿_20261020.md`
> **追加位置**：**§四「正确的做法（可复用）」之后、§五「留个物件」之前**，新增一节 **§四之二「声明自己会腐烂：声明也要接受机器检查」**。
> 命中理由：该条教训 §二.2 已写「凡是把『当前环境的数字』写进判据的地方，机器一变就腐烂」，§四.3/4/5 已给「合成自检 / 判据与地板分开 / 两条独立实现交叉验证」——本片段是**同一主题在同一场景下的新形态与新数据**，按「同主题不新建」纪律只出片段。

## 一、现象（真实数字）

本轮在「定时任务舰队」这套声明体系上，撞到了那条教训的**新形态**：不是「哨兵链接被修好了」，而是**声明本身没人读**。

1. **`baseline.value` 曾写 38 而实际 33，且无任何代码消费它。**
   探针不读、巡检不读、产物 JSON 里根本没有 baseline 字段。
   5 条 condition 被摘掉后没人回头改它 ⇒ **一个不生效的承诺**。它的危害不是「数字错了」，是它给了人「有人在盯这个数」的错觉，实际没人盯。
2. **文档里的「任务数」曾出现 38 / 45 / 52 / 53 / 54 / 58 六个不一致值**，散在技能文档、README、契约注释里。
   同一个事实有六个版本，且没有任何一个版本被机器校验过。
3. **三豁免叠加命中 6 条**：`allow_disabled=true` ＋ `max_age_minutes=0` ＋ 无产出断言。
   三条豁免单独看每条都有理由，**叠在一起**就成了「停用不管、不看新鲜度、不看产出」的永久真空区——这 6 条无论机器怎么变都不会红。
4. **`ok_results` 含非零码的 5 条**：非零退出码被白名单放行，却**没有任何理由**。
   放行一个非零码等于声明「这个失败可以忽略」，但没人写下它为什么可以忽略。

## 二、为什么是问题

- 与既有教训 §二.2 同源：**凡是把「当前环境的数字」写进判据的地方，机器一变就腐烂。**
  本轮的新形态是**腐烂的声明没有人看守**：探针不读、巡检不读 ⇒ 腐烂了不会有人知道，也不会有任何一条告警。
- 多个数字并存时，读者无法判断哪个是真源；**多分母**没有显式声明 ⇒ 「38 条」到底是「受监条件数」「registry 条目数」还是「文档自称数」，谁也说不清。
- 豁免不是不能有，但**豁免叠加**必须被机器看见；否则「绿」里就藏着一片没人负责的真空区。
- 非零码白名单**没有理由 = 没有责任人**。等真故障发生时，没人能判断这条是不是「已知例外」。

## 三、对策：声明也要接受机器检查

**核心一句**：声明不是写给人看的，是写给机器读的；**没人消费的声明等于没有声明**。

1. **L0 元探针（只读）**：新增一个专门查「声明是否还成立」的探针，把声明与现实做机器对账。
   本轮落地形态是四条断言：
   - `decl_baseline_mismatch`：声明的 baseline 与实际条数不一致 → 报；
   - `decl_registry_not_superset`：声明集合是否覆盖了登记集合；
   - `decl_triple_exemption`：三豁免叠加命中了几条；
   - `decl_doc_number_drift`：文档里的数字表述是否漂移。
   **只读、不改任何东西、不进熔断**——先把「声明会腐烂」变成可被看见的事实，再谈收紧。
2. **多分母**：一个数字对多个口径时，**必须显式写出各自分母**（受监条件数 / 登记条目数 / 文档自称数分别叫什么），否则跨文档引用必然打架。
3. **常数过期自检**：凡是把常数写进判据，必须标**实测日期与出处**；常数过期即报（与既有教训 §四.3「基准与哨兵要么改成合成自检，要么标上实测日期与出处」一致）。
4. **声明值改为派生**：静态数字迟早再漂；长线方向是让声明值**从实际条数派生**（派生 vs 声明的差集即漂移），而不是每次手工改。
5. **`ok_results` 逐码解释**：改造后要求每个被放行的非零码都必须有**逐码解释 ＋ `acknowledged_by`（谁认领了它）**。
   没有认领人的非零码不得放行——**未定性前一律不入白名单**，否则等于把真实故障一起洗绿。
6. **豁免叠加要显式**：单项豁免可以有理由，**叠加到第三层时必须有整体豁免说明**（谁批的、复查日期、什么时候撤）。

## 四、验证方式（含负例验证）

**正例**

1. L0 元探针能跑出上面四条断言的读数，且读数与人工核对一致（例如 baseline 声明值与实际条数的差、三豁免命中的条数、文档数字漂移处数）。
2. 探针**幂等**：同一天连跑两次，输出与判定不漂。
3. 探针**只读**：跑完不改动任何契约、registry、文档、计划任务。

**负例验证（关键）**

1. **baseline 负例**：把 `baseline.value` 故意改回 38（实际仍是 33）→ `decl_baseline_mismatch` 必须报 break（声明与现实不一致）。
   **若它不报，说明这条断言是装饰，不是检查。**
2. **文档漂移负例**：在文档里塞回一个旧数字（如把某处「任务数」改回 52）→ `decl_doc_number_drift` 必须报警。
3. **三豁免负例**：给任意一条 condition 加上 `allow_disabled=true` ＋ `max_age_minutes=0` ＋ 无产出断言 → 该条必须被 `decl_triple_exemption` 点名（叠加本身要能被发现，不能只报「有没有豁免」）。
4. **白名单负例**：把 `ok_results` 里某个非零码删掉且不写 `acknowledged_by` → 该条必须被拦下/报「待解释」，**不得默默放行**。
5. **过期常数负例**：把某个常数的实测日期改旧 ⇒ 常数过期自检必须报；否则「标了日期」也只是装饰。
6. **探针自身失效负例**：把探针产物的时间戳改旧 / 让探针跑不起来 → 消费方必须报「不可采信 / 过期」，**不得**把一份过期声明读数当成「声明仍然成立」。

## 五、适用边界

**成立的环境**

- Windows 本机 + PowerShell 5.1 + 无 Docker / 无 k8s；调度靠 Windows 计划任务；声明体系是 YAML/Markdown + 只读 PowerShell 探针。
- 声明里的数字能被机器重新数出来（任务条数、文件条数、条数宣称）。

**不成立 / 需要改做法的情况**

- 声明是**人工阅读的规范**、无法机器化对账（例如措辞规范、口径定义）→ 不入本条管辖。
- 数字来自**外部系统**且本机无法枚举（第三方 API 的配额数）→ 只能靠定期拉取 + 与人工核对，探针口径要另设。
- 没有稳定真源的「多份平行声明」（契约、registry、文档各说各话且没有指定真源）→ 本条只能**暴露**分叉，不能替人决定真源；真源归属必须先拍板。
- 需要修改声明才能让探针绿的场景**不适用**于「只读探针」定位：只读探针只负责报警，修不修由人决定。
