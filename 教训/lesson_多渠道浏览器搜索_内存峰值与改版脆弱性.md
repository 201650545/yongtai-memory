# 教训：多渠道浏览器搜索 = 内存峰值高 ＋ 改版即坏

> 郭老师原话（2026-10-21 14:12）：「每次开每个渠道，浏览器的内存压力暴增，
> 然后那些渠道总是一更新就出现问题，一点都不好用」

## 一、两条结构性原因（不是调参能解决的）

1. **内存是瞬时峰值，不是泄漏**：并发开 7 路 = 7 套浏览器上下文（每路自己的 profile/进程树）。
   实测：本机 Chrome 19 进程在任务期占 **3217MB**，任务结束即回落到 **2012MB**（少 1.2GB）。
   ⇒ 问题不是"忘了关"，而是**峰值本身**就能把整机顶到 90%+。
2. **"一更新就坏"是结构性的**：这类能力维护的是**网页 DOM / 文案 / 交互**，
   不是 API 契约。渠道改一次版（换文案、换选择器、改布局）适配器就失效 ⇒
   **维护成本永远压不下来**，属于结构性问题不是 bug。

## 三、替代路线（这就是"创新融合"的正确方向）

| 需求 | 用什么 | 代价 |
| :-- | :-- | :-- |
| 常规检索 / 每日资讯 | **纯 HTTP 源**：AIHOT（`aihot.news`，已在每天用）｜Hacker News API｜RSS | 零浏览器、极稳、天然抗改版 |
| 多方交叉验证 | **外部强模型**：ChatGPT 镜像站（GPT-6 Sol）｜Gemini 网页版（**均已实测可用**） | 不占本机浏览器，稳定性远高于网页适配器 |
| 必须登录 / 必须渲染 | 浏览器**单次、单渠道、用完即关** | 只在真需要时付这代价，**绝不并发多渠道** |

> **"多引擎交叉验证"这个诉求的正确解法是"多个强模型"，不是"多开浏览器引擎"**：
> 内存几乎不涨（模型在云端/自己网关里），且不随网页改版而失效。
> 2026-10-21 下午的 AIHOT 评审两轮就是这么做的（`external-model-review` skill，已实测）。

## 四、通用判据（以后选型先过这一关）

一个"要驱动 N 个第三方网页端"的能力，先问三句：
1. **峰值内存多少**？并发 N 套浏览器上下文的代价能不能接受？
2. **它维护的是什么**——API 契约（稳）还是网页 DOM（改版即坏）？
3. **有没有等效的"零浏览器"路线**（纯 HTTP / 强模型）？有就别用浏览器。
