# 教训：功能"点不到"比功能"坏了"更隐蔽

## 一、症状

经纬画布有两个动作「导出发布包」「归档本轮」：

- 代码**写了**（`client.js` 的 `openMenu` 里有这两个 `runAction`）；
- 接口**通了**（`POST /jingwei/actions/publish`、`/archive` 直接打都返 200，产物正确落盘）；
- 单测**全绿**（103 断言）；
- **但用户永远点不到。**

## 二、根因：两个条件互斥

入口的创建条件：

```js
// makeNode()
if (branch(n)) {                    // branch = n => n.kind !== 'merge'
  more.className = 'more';          // ⋯ 按钮
  more.addEventListener('click', () => openMenu(n.id, more));
}
```

菜单项的出现条件：

```js
// openMenu()
const actions = branch(n)
  ? [ ...重跑/查看/通过/打回/复制/删除 ]
  : [ ...查看/通过/打回/导出发布包/归档本轮 ];   // ← 只在这个分支里
```

`merge` 节点 ⇒ `branch` 为 false ⇒ **既进不了 else 分支给它的动作，也没有 ⋯ 按钮去打开菜单**。
而 `merge` 是每轮必有的收口节点 ⇒ 「发布/归档」整条路是死的。

## 三、为什么这个问题能活这么久

三个盲区叠加：

1. **读代码时的错觉**：在 `openMenu` 里看到 `导出发布包` 就认为"实现了"，不会去反查**谁能调它**。
2. **接口测试的错觉**：直接 `fetch` 打路由，200 + 产物正确 ⇒ 判"功能正常"。测试绕过了 UI，也就绕过了可达性。
3. **单测的错觉**：单测覆盖了 `publishRun()` 函数本身，同样不测"入口在不在"。

## 四、修法

1. **所有节点都给 `⋯`**（去掉 `if (branch(n))` 这层包裹，用裸块保作用域）。
2. **把动作放回语义正确的位置**：「导出发布包 / 归档本轮」从 merge 分支**移到 output 节点**——
   output 才是"把成果交出去"的地方，而且没有 merge 的图（如生图冒烟 `intake → art → output`）同样能用。

```js
const runActions = [];
if (roleOf(n) === 'output' && graph.runId) {
  runActions.push(
    runAction('导出发布包', false, () => publishRun()),
    runAction('归档本轮', false, () => archiveRun())
  );
}
```

3. **验证方式不是读代码，是列矩阵**：对每个节点类型（intake / produce / verify / merge / audit / output）
   实际打开菜单，把拿到的按钮清单打印出来比对。实测结果：
   - `output` = 重跑/查看/通过/打回/复制/删除/**导出发布包/归档本轮**
   - `merge` = 查看/通过本轮/打回
   - `intake` = 重跑/查看/通过/打回/复制/删除（无发布动作）
4. **最后还必须真点一次**：点「导出发布包」看 `publish/<runId>/` 是否生成；点「归档本轮」看 `index.json` 是否更新。

## 五、可迁移的判断力

1. **"实现了"≠"可达"≠"可用"**。三者的验收方式完全不同：实现看代码、可达看入口矩阵、可用看真点。
2. **凡是"条件渲染的入口"配"条件渲染的菜单"，都要问一句：这两个条件会不会互斥？**
   会 —— 那就是这里。检查方法很机械：把入口的 `if` 和菜单项的 `if` 并排放，看有没有一个分支既不给入口、又只在这个分支里给动作。
3. **接口测试天然绕过 UI，所以它的绿灯不能证明功能可用**。凡是"有个用户入口 → 触发一个后端动作"的功能，必须走一遍 UI。
4. 顺带一个心智模型：**动作应该挂在它语义所属的节点上**，而不是"顺手写在哪里"。
   发布属于"交出去"= output，不属于"收口"= merge。写错位置是这次 bug 的源头诱因。
