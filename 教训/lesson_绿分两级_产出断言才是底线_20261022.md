# 「绿」必须分两级：进程级成功 vs 产出级成功

> **一句话结论**：「绿」必须分两级：进程级绿≠产出级绿，底线是 L3 内容级断言。

## 一、现象（真实数字）

本轮改造的是元智能「受监定时任务舰队」的巡检口径（33 条受监任务）。

- **改造前**：33 条受监任务里 `asserted_green = 0`、`process_only = 27`。
  也就是说：一条都没有产出级证据，全部 27 条只是「进程没报错」。
  一轮巡检报出来的「绿」，没有一条能回答「产物到底对不对」。
- **改造后（2026-10-22 08:00 前后）**：`asserted_green = 13`、`process_only = 11`、`asserted_fail = 2`、`unknown = 0`。
- **两条 `asserted_fail` 是真实失败，不是断言写错**：
  - `balancewatch`：`quota_guard.json` 停在昨天（文件还在，内容停在昨天 ⇒ 旧口径看不出问题，新口径判红）。
  - `modelscope_daily_guard`：`"all_granted": true` 只在 2026-08-10~13 出现过，已约 10 万分钟未更新。

关键现象不是「红了几条」，而是**红得对**：新口径第一次把「跑了但没产出／产出是旧的」这两类真实故障从绿里摘了出来，
而且 `unknown` 归零——每条受监任务要么有产出级证据，要么有明确的失败证据，没有「不知道算不算绿」的中间态混进绿里。

## 二、为什么是问题

1. **「全绿」从来不是一种东西。** 同一个绿里混着两种事实：①进程级成功（脚本退出码 0、没抛异常）；②产出级成功（产物在、内容对、是本次的）。
   混着报 ⇒ 读报告的人分不清「这一轮我核对过」还是「这一轮只是没报错」。
2. **L1（存在）与 L2（mtime）单独用，等于没断言。**
   - 只判「文件存在」：旧文件永远存在 ⇒ 永远绿；
   - 只判「mtime 新鲜」：脚本每次都写同一个文件、只是把内容换成一个空壳或上一次的结果 ⇒ 照样绿；
   - 真正的底线是 **L3 内容级**：产物里必须出现「只可能由本轮成功运行产生」的标记（日期/时间戳/本次专属字段）。
   - 本轮采用的做法是**一律双断言**：`file_fresh`（证明「跑过」）＋ `text_regex`（证明「跑对」），缺一条都不算 `asserted_green`。
3. **判定字段必须显式，不能靠默认。** 缺 `artifact_state` 的旧格式产物**不许**默认当成「仅进程级」——
   默认值会让总数虚高，那只是把「凑数」换了个马甲。缺字段就是缺字段，宁可让它不落桶。
4. **加断言必然带来假红风险，所以必须负例验证。** 阈值放宽（比如把新鲜度窗口放很大）等于把断言稀释回「等于没断言」。

## 三、对策（怎么落地）

### 3.1 字段

| 字段 | 位置 | 作用 |
| :-- | :-- | :-- |
| `artifact_assertions` | 契约（`ops-task-fleet.yaml`）的每条 condition | 声明这条任务的产出级判据（`file_fresh` + `text_regex` 等） |
| `artifact_state` | 探针产物（drift JSON）每条 condition | 判据求值后的结论：`asserted_pass` / `asserted_fail` / `unasserted` / `unknown` 等 |
| `artifact_expectation` | 契约（可选） | `unknown_by_design` / `not_applicable`：明说「这条不该有产出级断言」，免得被当成漏做 |

### 3.2 状态机与绿分两级口径

```
artifact_expectation 声明为 unknown_by_design / not_applicable ──▶ unknown（单列，不计入绿）
无 artifact_assertions 声明（unasserted）                     ──▶ process_only（仅进程级）
有 artifact_assertions 且求值通过                              ──▶ asserted_green（已断言）
有 artifact_assertions 且求值不通过                            ──▶ asserted_fail（真红）
```

- `asserted_green` ＝ level=info **且** `artifact_state` 表示「有断言且通过」。
- `process_only` ＝ level=info **且** `artifact_state=unasserted`（只有进程级通过，没有任何产出证据）。
- `unknown` ＝ level=unknown，**单列，不计入绿**。
- 「断言通过」只认字面 token，缺 `artifact_state` 字段的旧格式产物**一律不算有证据**。
- 判红逻辑本身一个字不动：绿分两级只是把结果分桶，不改任何一条条件红不红的判定。

### 3.3 落地纪律

- **先取证再写断言**：先把「这条任务的产物到底是什么、在哪、内容里哪个标记只可能由本轮产生」查清，再写判据。
- **双断言不许省**：单用 `file_fresh`（只判文件新鲜、不判内容）在本轮盘点出的多条任务上都会假绿——文件是新的，内容却是上一次的。
- **追加型日志必须按「当天段落」切段**：否则断言等于「历史上曾成功过」。
- **共享面文件禁止用于归因**：多个任务共写的同一个日志文件不能作为某一条的产出证据。
- **人工补跑过的任务按「定时时刻窗口」判**，不能用「24 小时内」。
- **每条断言都要能说清「它什么时候会红」**，否则它多半是永绿断言。

## 四、验证方式（含负例验证）

**正例**

1. 口径闭合：同一轮内 `asserted_green + process_only` 必须等于该轮 `info` 条数（不漏不重）；不成立 ⇒ 分桶口径与探针口径分叉了。
2. 改造前后对照：改造前 `asserted_green = 0` / `process_only = 27`；改造后 `asserted_green = 13` / `process_only = 11` / `asserted_fail = 2` / `unknown = 0`。
3. 红得对：两条 `asserted_fail` 经人工复核确认是真失败（`balancewatch` 的 `quota_guard.json` 停在昨天；`modelscope_daily_guard` 的 `"all_granted": true` 只在 2026-08-10~13 出现、已约 10 万分钟未更新），不是断言写错。
4. 既有消费方不破：巡检 GATE 行既有字段的名字、顺序、数值一个字未动，新字段只追加在末尾。

**负例验证（关键，缺这条就等于写了永绿断言）**

1. **阈值负例**：把某条已通过的断言的新鲜度窗口改到 1 分钟（或把正则改成一条产出里永远不会出现的字符串）→ 该条必须由 `asserted_pass` 转 `asserted_fail`。
   **若它仍然绿，说明这条断言是空跑（恒真），必须作废重写，而不是记成「稳定通过」。**
2. **缺失字段负例**：拿一份缺 `artifact_state` 的旧格式 drift 产物喂给巡检 → 该条**不得**进 `asserted_green` 桶，也**不得**默认补成 `unasserted`（只能不落桶）。若它被算进「已断言」⇒ 白名单被放宽了。
3. **旧产出负例**：把某条任务的产出文件回滚成上一次的内容（内容是旧的、文件在、mtime 也可能被触碰）→ 该条必须红。
   这一条专治「只判存在」和「只判 mtime」两种假绿。
4. **豁免负例**：给某条 condition 加上 `max_age_minutes=0` 之类的放宽后，它是否仍然能被判红？不能 ⇒ 豁免在吃断言。

## 五、适用边界

**成立的环境**

- Windows 本机 + PowerShell 5.1 + 无 Docker / 无 k8s + 调度靠 Windows 计划任务。
- 任务的产出是**本地文件 / 本地日志**，可被只读探针直接读到的。
- 判据可以用「文件存在 + mtime + 内容正则」表达，且产出里确实存在「只可能由本轮成功产生」的标记。

**不成立 / 需要换做法的情况**

- 产出在远端、网盘或数据库里，没有稳定可读的本地文件 ⇒ L1/L2/L3 三级断言要换成拉取 + 查询断言。
- 任务本身是常驻服务（不是每天跑一次的批处理）⇒ 进程级绿本身就是有意义的信号，不需要强行产出级断言。
- 任务是人工触发的、没有稳定调度周期 ⇒ 新鲜度窗口与「应到未到」判据都要另设（见心跳缺席那条）。
- 产出是追加型日志且无「当天段落」标记 ⇒ 本条判据不适用，硬加会假绿（追加型日志必须先能切段）。
- 需要判断「跑没跑」而不是「产出对不对」⇒ 属心跳缺席那条的管辖范围，本条只管产出级。
